# 机械臂通信协议说明 V0.3 —— 梳理

> 来源：`docs/机械臂通信协议说明_V0.3.pdf`（原文 PDF，本文件为结构化梳理 + 与本项目的对照注记）。
> 「原文如此」标注协议文档本身的问题；「本项目注记」是接手时需要知道的坑。

## 一、基本说明

- 通信方式：TCP，client（调用系统）→ server（机械臂系统）
- server：`192.168.10.95:30485`
- 帧格式：`json数据域 + 帧尾`，帧尾为单个字符 `#`

| 名称 | 内容 | 描述 |
|---|---|---|
| 数据域 | json 序列化数据 | — |
| 帧尾 | `#` | — |

**本项目注记**：TCP 30485 是**单连接**，跑 `joint_probe.py` 前必须先停 T3 bridge（AGENTS.md §4）。

## 二、帧内容（14 条命令）

通用约定：

- `joint`：1-17 关节角度，单位弧度，顺序为 **腰/L1-L7/R1-R7/摇头/点头**，`-100` 表示该关节不移动
- `pose`：left TCP `(x,y,z,qw,qx,qy,qz)` + right TCP `(x,y,z,qw,qx,qy,qz)`，`-100` 表示该臂不移动
  - 原文如此：pose 的单位写着「弧度」，实际应为米/四元数无量纲
- `v`：速度百分比例系数 0~100
- `status`（server 应答）：`program_run_finish` / `program_run_failed`

| # | 命令 | 方向 | 关键字段 | 说明 |
|---|---|---|---|---|
| 1 | `movej` | C→S | `joint[17]`, `v` | 关节运动（阻塞式） |
| 2 | `movej_canfd` | C→S | `joint[17]`, `freq` | 角度透传（流式），`freq` 为下发频率 |
| 3 | `movej_p` | C→S | `pose[14]`, `v` | 关节空间规划到目标位姿 |
| 4 | `movel` | C→S | `pose[14]`, `v` | 直线运动 |
| 5 | `get_joint_position` | C→S | — | 返回 `joint[17]` + `status` |
| 6 | `get_tcp_pose` | C→S | — | 返回 `pose[14]` + `status` |
| 7 | `get_device_state` | C→S | — | 返回错误码（见下） |
| 8 | `get_config` | C→S | — | 返回 `upperLimits` / `lowerLimits`（软限位） |
| 9 | `stop_motion` | C→S | — | 轨迹急停 |
| 10 | `clear_fault` | C→S | — | 清除错误 |
| 11 | `enable_robot` | C→S | — | 上使能 |
| 12/13 | `disable_robot` | C→S | — | 下使能（文档重复列了两次） |
| 14 | `set_zero` | C→S | — | 设置零位 |

### get_device_state 返回字段

- `erroeCode`（原文拼写如此）：`0x00` 正常 / `0x01` 硬件错误 / `0x02` 软件错误
- `hardwareErrors`：如 `0x01010001` = 第一个电机掉线
- `softwareErrors`：如 `0x02010001` = 第一个电机超软限位

### get_device_state 字段证据补充（协议梳理与现场记录分层）

> 纠正：本 Markdown 梳理的早期版本只摘录了 erroeCode、hardwareErrors、softwareErrors，漏列了 state 和 motorErrorDetails。这属于本梳理的字段记录不完整，不能据此推断控制器不会返回这两个字段。

仓库已有现场证据：

1. **故障状态完整响应**：TASKS.md 的 T28 保存了 2026-11-06 16:10 的原始响应，包含 state="fault"、motorErrorDetails 对象数组、hardwareErrors 非空及 erroeCode=1。示例：

```json
{
  "command": "get_device_state",
  "erroeCode": 1,
  "hardwareErrors": [17235970],
  "motorErrorDetails": [
    {
      "general_desc": "电机7 报错",
      "hardware_error_code": 17235970,
      "motor_detail_code": 8,
      "motor_detail_desc": "堵转",
      "motor_id": 7
    }
  ],
  "softwareErrors": [],
  "state": "fault"
}
```

2. **故障清除后的局部状态证据**：WORKLOG.md 记录 2026-11-06 16:19 的响应片段 motorErrorDetails=null、softwareErrors=[]、state="ready"。同一记录说明当时仍未使能，运动命令被拒；随后由操作员执行 enable_robot 后状态变为 idle。
3. **状态字段不能单独代表无故障**：WORKLOG.md 记录 2026-11-06 17:44:40 的原始响应：state="idle"，但 erroeCode=2、softwareErrors=[34013185]。因此只看 idle 不能判断设备无故障，更不能把 idle 等同于已使能。
4. **完整健康态样本仍缺**：当前可检索的历史记录没有提供一份完整、无故障的 get_device_state 原始报文；协议梳理中 erroeCode=0 的定义和离线模拟样本不能替代现场健康态原始证据。

| 字段 | 当前证据 | T33 的安全处理 |
|---|---|---|
| state | 现场出现过 fault、ready、idle；完整状态枚举/转换规则未收齐 | 仅接受 idle / ready；其他或缺失均拒绝 |
| erroeCode | 厂家拼写为 erroeCode；现场故障记录有整数 1、2；协议梳理记载 0/1/2 分类 | 要求整数 0；兼容别名 errorCode，任何冲突/非零值均拒绝 |
| hardwareErrors / softwareErrors | 现场原始响应为数组，可能包含错误码 | 必须存在且均为空数组 |
| motorErrorDetails | 故障时为对象数组；故障清除后曾为 null | 字段必须存在，且只能为 null 或空数组 |
| status | 现场查询应答可带 program_run_finish | 由 RPC 层核对命令对应关系及成功状态 |

**命令边界必须分清：**

- #7 get_device_state：查询设备状态/故障信息。
- #8 get_config：单独查询软限位配置。
- #11 enable_robot：单独上使能。
- #12/13 disable_robot：单独下使能。
- #10 clear_fault：单独清故障。

以上不是 get_device_state 的附带动作。T33 只读预检只发送查询命令；采样流程也不自动清故障、上使能或下使能。使能状态必须由现场操作员通过示教器/5566 等现场界面确认，不能仅凭 state 推断。完整状态机、各固件版本字段差异及电机明细对象的正式 schema 仍需厂家补充或现场持续取证。

## 四、本项目注记（接手必读）

以下为 V0.3 文档未覆盖、但现场已验证的事实（对照 HANDOFF / 记忆档案）：

1. **`movej` 不可用于遥操**：50Hz 连发会因程序重叠被拒（`program_run_failed`），遥操定版基线是 `movej_canfd` 流式（拒绝 2340→0，40-50Hz）。
2. **`-100` 占位轴坑**：movej 系列里 `-100` 表示该关节不动，但 movej_canfd 方案里有 `-100` 占位轴被拒的坑（AGENTS.md §1），不要在没有新证据的情况下使用。
3. **`get_joint_position` 的应答不能解锁 lock-step**（T03 设计约束）：它的应答不代表运动完成。
4. 文档里 movej/movel 的 6 轴示例实际仍发 17 元数组——示例与字段说明存在不一致，以真机实测为准（未验证具体差异）。
5. 软限位经 `get_config` 动态获取已接线（T23），本地实现未部署，2 测试挂起。
