## 一、实时性 / 跟手性（调优占比最大）

| 问题 | 根因 | 解法 |
|---|---|---|
| 双臂使能剧烈抖动 (C-001) | 求解与 500Hz 发布共用单线程，发布被饿出 20~130ms 间隙 | 求解搬专用线程 |
| 目标断流后冻结→猛冲 (C-002) | 恢复后 IK 种子=旧解 | 断流重锚定 `target_stall_reanchor=0.3s` |
| Puppetry 忙等一顿一顿 (P-003) | `interval_ms=2`(500Hz) 忙等吃满一整核 | **降频 500→100Hz**，CPU 87%→8%，信息量无损 |
| renice 重启失效 (P-004) | 启动脚本没带 nice | 启动脚本固化 `nice -n 10` |
| 静止双臂高频细颤 (P-007) | 双臂轮转挤占单求解线程 + 限速器自激极限环 | per-arm 独立求解线程 + 低通 fc=15Hz + 死区固化 |
| 真机卡顿但频率全达标 (P-021) | `.3` SSH 进的是共享 CPU 命名空间，load 36 来自不可见的其他环境 | taskset 绑核 + 停影子录制（缓解） |

## 二、IK 求解质量

- **姿态反人类 (C-006→P-001)**：纯求解无姿态代价 → 多构型枚举+姿态代价选优（natural）；v2 删掉代价后姿势回归，v3 恢复+300ms 去抖。教训：**删功能比加功能更容易回归**。
- **肘贴躯干 (P-013)**：新增 `elbow_tuck` 几何代价项（默认 0=零变化，按权重灰度上线）。
- **停不准/偶发跳变 (P-014)**：跳变实为静默拒解冻结后 ≤2s 追赶，非单帧跳变 → 目标死区 3mm + 追赶坡化（峰值速度 −70%）。
- **低位 13~24% 拒解根治 (P-016)**：pink QP 差分 IK 后端，`IK_BACKEND` 一键切换旁路部署。
  - M3 大坑：**Pink 3.5.0 + pip Pinocchio 连续求解 native segfault → 必须复用 ROS Pinocchio 4.0，`pin-pink --no-deps`**；验收标配 500 步连续求解自检。
  - M4：Python GIL 串行化两臂 OSQP 仅 63.9Hz → per-arm 双进程 187Hz。
  - M5 修三根因：漏 X_map 帧变换致 ~1m 偏差、URDF 末端漏 Rz(π/2) 恒差 90°、离合未踩不发命令致 devmode 会话掉线。

## 三、启动链路 / 状态流（"能启动但不动"类）

- **四因链 (P-018)**：①旧 MessageBridge 残留占 TCP 9900 致 bind 失败静默继续 ②设备重启后 Hub 须强制重注册（约 60s 才进数据）③devmode 关则 robot_state 断流 ④重启后 clutch 锁存 true。教训：跨主机验证结束必须清理临时进程。
- **one_key_start 死锁 (P-015)**：脚本顺序 bug——先等 robot_state(20s) 才开 developer_mode，而模式关时运控不发 robot_state。鉴别口诀：**状态无数据先查模式**。
- **运控断流+服务瘫痪 (P-011)**：一天 3+ 次无预兆断流，反复开关 devmode 会瘫痪，唯一恢复=整机重启；developer_mode 服务只在模式=关时回包（勿误判为死）。恢复流程入 DEPLOY 7.5。
- **SDK QoS 坑 (P-022)**：`/mc/sdk/robot_state` 是 BEST_EFFORT，订阅用默认 RELIABLE 收不到（静默无数据）。
- **本机 EtherCAT (P-039)**：主站开启失败 40s 超时 = ENI 37 从站 vs 实扫 36，左手腕 EcatToCan 线未接（经 Loki 日志 `ecatScanBus() Error` 定位）。
- **developer_mode 门控 (P-036)**：一键启动阻塞于开发者模式服务连不上，先修服务再谈下游。

## 四、灵巧手 / 手套（条目最多、反复复发）

- **行程不足 (P-024/P-028)**：MessageBridge 归一化不覆盖 [0,1] → 改 `use_raw_glove=true`，raw 通道按实测端点重归一化 + 无效通道排除（span<0.15 剔除）。
- **标定只在进程内，重启即丢 (P-031)**：raw 端点标定 YAML 自动保存/启动加载 + 双 Clutch=false 门禁。真凶另有其人：**三代灵巧手启动时突然闭合顶死限位锁死整手**（设备行为，与手套标定无关）。
- **通道映射偏置 (P-032)**：左手 ring 用 ch9/ch10/ch11 max 聚合，ch9 饱和归一化=1 主导目标 → 生产 YAML 剔除 ch9。
- **复发 (P-043，最有教学价值)**：P-032 修复只改了 YAML 没进代码，重标定时 `FinishCalibration` 无条件回写 valid=true → **配置修复必须固化进代码，否则一次重标定就复活**。终解：`forced_invalid_channels` 参数 + 在 Save 之前 Apply + 回归测试锁行为。
- **拇指顶死卡滞 (P-038)**：`kJointMax[thumb_mcp]=1.01` 过大 → 收缩到 0.70（隔离构建+23 项回归+SHA256 原子替换正式二进制）。
- **标定失败被当有效 (P-030)**：`calib_valid=false` 时 `norm()` 返回 0，死通道被当 0.588 rad 恒定目标顶死上限 → 钳位止血 + 重标定状态机（禁止降门槛放行死通道）。
- **食指瞬时卡滞 (P-029)**：证据只证明最终可到位，不证明卡滞消失；原因明确前不提高关节上限、不放宽跟踪误差阈值。

## 五、硬件事故

- **P-008 拇指断裂（最重事故）**：B 键复位试摆，臂模型裕度显示"安全 117~269mm"但灵巧手未建模（手被当腕后 8cm 单点）→ 碰撞断裂。
  - 深层教训：**安全层未闭环就不执行真实运动**。
  - 重启前置：手部几何建模（V2 mesh 0.131×0.071×0.100m，35 个 STL 已入仓）+ FK 硬接入运动循环 + 逐段用户目视。
  - 与 P-019（右手整手失效，effort 恒 0、疑同源碰撞损伤）合并报修（P-010）。

## 六、部署 / 迁移 / 环境

- **pink venv 配方 (P-016/P-047)**：`pin-pink --no-deps` 是红线；P-047 发现新安装器违反此定案（装 pip pin==2.7.0 且未 --no-deps），照安装器部署的新设备有同款崩溃风险。
- **进程在线≠能干活 (P-034)**：复位客户端活着但缺 OMPL 插件根本不能规划 → 补装；**不以进程存活做验收**。
- **五连败故障串 (P-023)**：缺 pinocchio 秒退 / 预检双引号吞 PYTHONPATH / venv 缺 jinja2（osqp 硬依赖，只在 Clutch=true 才调 solve 所以启动"看似正常"）/ 门禁 `topic hz` 只给 3s 且无 pipefail 被 head 掩成成功 / 兜底经验=优先重启运控。
- **依赖安装一键化 (P-037)**：阿里云优先失败转清华镜像回退 + `--check/--dry-run/--verify-built`。
- **统一入口 (P-009/P-023/P-035/P-044)**：机器人本地菜单 + 源码编译入口；控制台兼容多布局；修 `pkill -f` 同 SSH 自杀（拼接关键字）。
- **架构评估 (P-017)**：宿主机→容器 TCP 可行（0.657ms/0% 丢包），但宿主机 aarch64，x86 Puppetry 不可用——先查架构再选型。
- **收工必对账 (P-025/P-045)**：真机定版改动未提交=丢代码风险（已两次取回）；**合成 URDF 副本没随修复同步**，从仓重建即复发——好在有启动门禁拦截成"卡部署"而非静默危险。
- **迁移工具化 (P-027/P-033)**：分步脚本 + DRY_RUN + SHA-256 校验 + ARM/x86 架构门禁 + 首次启控不自动执行。

## 九、最有迁移价值的六条方法论

1. **降频优于加线程**：500→100Hz 解决大半卡顿（信息量无损时）。
2. **环境配方钉死**：`--no-deps`、Pinocchio 版本、venv——任何新安装路径（安装器/新设备/文档）都可能违反定案，部署 SOP 要显式警示冲突。
3. **配置修复必须固化进代码+回归测试**，否则被标定/重启复活。
4. **进程在线≠功能正常**，验收看行为证据（连续求解自检、topic hz 带 pipefail、满行程动作）。
5. **安全模型必须覆盖末端执行器几何**，"裕度安全"不含手=事故。
6. **单连接/单实例资源是重灾区**（TCP 端口残留、模式门控、锁存状态）——"能启动但不动"先查残留进程和状态锁存。
