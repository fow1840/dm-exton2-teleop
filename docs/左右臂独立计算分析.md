# 左右臂独立计算：UBT 为什么这么做，DM-EXton2 是否需要

- 日期：2026-11-06（离线分析 + 代码实证，未连真机）
- 依据：UBT LEDGER(-ARCHIVE)、docs/diagnostics（C-001 / P-003 / P-007 / P-016 M2~M5）、
  本仓库代码锚点、本项目 WORKLOG 调试经历
- 结论分级：✅=证据实证；🔍=推断（量级估算，待测量）；⬜=未验证

---

## 一、UBT 做左右臂独立计算的四个原因（决策链完整回放）

### 原因 A：算力/实时性——双臂顺序解算挤占单线程，双臂才暴露（✅ 三次独立实锤）

| 事件 | 现象 | 定案 |
|---|---|---|
| **C-001**（2026-10-10，SDK IK 时代） | 双臂使能**剧烈抖动**；单臂使能不抖 | natural 重求解与 500Hz 发布共用单线程执行器 → 双臂使能让发布线程饿出 **20~130ms 间隙** → 运控收到的位置指令断续 →「一顿一顿」。修复=求解搬专用线程 |
| **P-007**（2026-10-12） | 双臂静止**高频细颤**（10~14.7mrad）；单臂/不使能都不抖 | 四组真机对照（不使能/仅左/仅右/双臂）+ 离线参数扫描 + 降频实验逐项排除 → 定案：**双臂轮转挤占单求解线程 → 周期超限 + 限速器自激极限环**。根治=per-arm 独立求解线程，用户验收「很很明显的改善」 |
| **P-016 M4/M4.5**（2026-10-13，pink 时代） | pink 影子仅 63.9Hz（目标 100Hz），`Loop skipped` 321 次 | `.3` 真机基准四档并行粒度：单臂 3.1ms / **顺序双臂 5.7ms（理论上限 176Hz）** / 两线程被 **GIL 反拖到 101~104Hz（线程无效）** / **两进程 253.7Hz**。定案：**per-arm 独立进程**（pink/OSQP 是 C 扩展但受 Python GIL 串行化，多线程反而更慢） |

**关键教训**：这三个问题全部是「单臂正常、双臂暴露」——只测单臂永远发现不了。

### 原因 B：共享状态耦合（✅ M2 审查发现）

P-016 M2 审查：pink 版 ik_node 左右臂在**同一个 timer 的 control_loop() 内按 left→right
顺序执行两次 FK+QP**，且 `last_velocity` 为双臂共享向量、**任一臂 clutch 上升沿会
fill(0)，扰动另一臂滤波历史**。建议上机前拆 per-arm 状态。

### 原因 C：故障隔离与独立诊断（✅ 现场事件）

- M2 改造：命令桥**独立监听左右原始 Pose 心跳**，任一路超时只停该臂；
- M5 C-004：per-arm 分消息臂检测（pink 两进程各发 7 关节，桥按 name 拼回 14 关节，
  检测本消息含哪条臂、缺臂不误报）；
- 2026-10-14 复现事件：左 Clutch=true 后左 target STALE、**右臂全链路 OK**——
  per-arm 独立性让「单臂故障不影响另一臂」且证据链可直接归因；
- 安全门 per-arm：`ArmSafetyGate` × 2 实例，fault_latch 按臂锁存（单臂越限不连坐）。

### 原因 D：消息语义（✅ 架构选择）

UBT 命令流 `robot_command` 内每关节独立（JointCmd per name）→ per-arm 天然可行；
`joint_commands` 话题两进程各发 7 关节，桥按 name 拼回。

## 二、DM-EXton2 是否存在同样需求：逐项对照（✅ 代码实证）

### A. 算力/实时性——**存在，且更紧**（🔍 容量估算，待 T18 测量）

| 项 | UBT pink（出事时） | DM-EXton2 现状 |
|---|---|---|
| 解算结构 | 单 timer 顺序双臂 FK+QP | **同构**：`ik_node.py:386-509` 同一 250Hz timer 顺序 left→right |
| 目标频率 | 100Hz（预算 10ms） | **250Hz（预算 4ms）——比 UBT 出事时还紧 2.5 倍** |
| 同栈基准 | 单臂 3.1ms / 双臂顺序 5.7ms | 同 pink/osqp/ARM64 栈，数字可直接参考（🔍） |
| 双臂同动预算 | 5.7ms < 10ms ✓（但限速器仍自激） | **5.7ms > 4ms ✗ → 双臂同按住同动时 250Hz 必然掉频**（预估掉到 ~175Hz 以下；M4 影子实测含 FK/发布开销 p99 13~31ms 更悲观） |
| 缓解现状 | — | 只对按住臂 solve + 手静冻结跳过 → 双臂**同静**无压力；**双臂同动=最坏情况** |
| 真机数据 | 四组对照齐全 | **右臂从未测过**（WORKLOG 23:01 明记「右臂未测」；20 个基线包 + press01~04 全是单臂） |

**结论**：双臂同时运动（数采主场景）的容量缺口是可预判的，只是尚未被任何一次测试暴露。

### B. 共享状态耦合——**存在，且比 UBT 当年更重**（✅ 代码语义确定，⬜ 幅度未测）

`ik_node.py:387-393`（任一臂离合上升沿分支）：

```python
if self.clutch[side] and not self.prev_clutch[side]:
    self.q_commanded = self.q_measured.copy()   # ← 重置的是两臂全量！
    self.last_velocity.fill(0.0)                # ← 清的是两臂全量！
```

**后果推演**：右臂正在跟手（IK 持续积分、指令领先实测数度）时，操作员按下左离合 →
右臂的 `q_commanded` 被瞬间重置回真机实测位 → 右臂指令出现一个反向跳变（幅度=当时
跟踪误差，可达数度）→ bridge 限幅 0.2rad/帧 追认 → **右臂可见地顿/跳一下**。
`last_velocity` 清零再叠加右臂速度滤波一拍突变。
UBT M2 当年只发现了 `last_velocity` 一半；本项目的 `q_commanded` 全量重置是同型且
更重的另一半。**单臂测试永远触发不了**（另一臂不在跟）。

### C. 故障隔离——**协议层存在「连坐」结构限制**（✅ 协议事实）

- 本机协议 17 维一条 movej = **两臂同进一个程序**：任一臂触发 `program_run_failed`
  （如左 J7 限位、程序重叠），**整帧拒绝，右臂同帧收不到新指令**（T12 期间拒绝
  19→59，右臂是否同窗停发值得回查日志）。
- UBT 的 JointCmd per-name 消息没有这个问题；DM-EXton2 的 per-arm 独立性上限受
  协议约束。可行降级：某臂异常时其 7 槽发 `-100`（协议定义=该关节保持），只送
  另一臂——**movej 模式腰/头槽一直在发 -100 无异常，臂轴 -100 行为待真机验证**（⬜）。

### D. bridge 层状态耦合（✅ 2026-11-06 重构后仍有一处）

`StepPlanner` 的 leash `worst` 跨两臂取 max → **左臂超限会冻结整帧（连坐右臂）**；
`invalidate()` 清全 17 维（协议整条拒，属诚实语义，保留）；hold 锁已按轴独立。
per-arm leash 可改（见 T19）。

## 三、结论与行动

1. **同样的需求存在，且三类问题（A 算力、B 状态耦合、C 隔离）在 DM-EXton2 都有
   对应物**；差异只在协议层（17 维一条 movej）把「隔离」的上限压得更低。
2. **最大风险 = 双臂同时运动从未测过**，而 UBT 的三次教训全部在双臂场景暴露。
   按「先测量再改造」纪律：先 T18 测量（双臂同动时 IK 频率/loop 耗时 + 按左离合时
   右臂是否跳变），再决定改造深度。
3. 离线可预备的已入 T19（见 TASKS）：`q_commanded`/`last_velocity` **按臂重置**
   （B 修复）、`StepPlanner` **per-arm leash**（D 修复）——两者均已实现并离线回归；
   per-arm 进程拆分（A 根治）等 T18 数据再动（ik_node 参数化 `side` 即可单文件支持
   两实例，不必拆文件）。

## 四、UBT 经验的适用性边界

- GIL 基准数字（3.1/5.7ms）来自 Walker S2 的 7-DOF 模型与 .3 主机，DM-EXton2 模型
  规模相近但 URDF 不同——只能作量级参考，**T18 必须实测**；
- UBT 的 per-arm 进程拆分动机里有一条是「分臂发布 7 关节」的协议配套，DM-EXton2
  没有这个配套需求（话题本来就是 14 关节一条），拆分的唯一动机是算力——改造可以
  更轻（参数化 side，两实例各解算各臂）；
- UBT 的「桥按 name 拼回」DM-EXton2 的 bridge 天然支持（`name_to_pos` 按名匹配，
  两实例各发 7 关节无需改桥）。
