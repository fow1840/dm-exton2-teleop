# 机器人现场调试手册 —— 快速实验驱动模式

> 生效：2026-11-07。适用：DM-EXton2 及后续机器人的现场调试、设备适配、功能联调。
> 本手册只管**工作方式**。操作规矩、访问方式、踩坑清单见 [AGENTS.md](../AGENTS.md)；
> 任务状态唯一权威在 [TASKS.md](../TASKS.md)；动作与证据落 [WORKLOG.md](../WORKLOG.md)。
>
> **总纲：大胆假设、小步修改、快速验证、有效保留、无效回退。**

---

## 1. 核心原则

在机器人现场调试、设备适配和功能联调过程中，优先采用**假设驱动、快速验证**的工作方式。

- 核心目标是**尽快让设备达到预期运行效果**，而不是在修改代码之前完成所有理论分析。
- 不要求每次修改前都完全定位根因，但要求**每次修改都有明确的验证目标**。

## 2. 调试流程

**适配前置门禁（P0）**：任何 URDF 在接入遥操链（IK/限位/碰撞/RViz）之前，必须先过
附录 C 的真机验收（五道门）——**URDF 正确性是适配前优先检查对象**，不合格 URDF 进链路
是方向反、跟丢、限位 fault 的总根源（T20 实锤），靠调参数救不回来。

遇到问题时，按以下顺序执行：

1. 简要理解当前问题和预期效果。
2. 提出**最值得优先验证的一个**假设。
3. 给出**最小化、可逆**的代码或参数修改方案。
4. 明确修改位置及预期效果。
5. 优先安排真机验证。
6. 根据实际效果决定保留或回退。
7. 如果无效，快速切换下一个假设。

## 3. AI 的行为要求

- 不要一开始就进行大篇幅的理论分析。
- 不要在没有必要的情况下分析整个项目架构。
- 不要为了追求根因而长时间停留在推理阶段。
- 不要一次性罗列大量可能原因。
- 优先提出最可能有效、修改成本最低的方案。
- 每次优先只修改一个变量。
- 不要未经验证就宣称问题已经解决。
- 当现有证据不足时，优先设计**能够区分不同假设的实验**，而不是继续推理。

## 4. 实验验证要求

每次实验开始前必须能回答五个问题，缺一不动手：

| 问题 | 要求 |
|---|---|
| 当前假设是什么？ | 一句话，可被证伪 |
| 修改了什么？ | 文件 + 位置 + 内容，**单变量** |
| 预期效果是什么？ | 指标级，可观测 |
| 如何判断成功或失败？ | 事先定好判据，不许事后解释 |
| 如果失败，如何回退？ | 精确到命令 / 文件 |

涉及真实机器人时，必须先满足安全测试条件（见附录 B）：优先**低速、小位移、有限工作空间**验证。

### 4.1 实验记录（落 WORKLOG.md，沿用既有模板 + 实验五问）

一条实验 = 一条 WORKLOG 记录，标题建议编号 `ExNN`（在对应 Txx 任务下递增）：

```
## YYYY-MM-DD HH:MM | Txx / ExNN 假设：<一句话> | AI / 操作员

- 假设：<改 X 会让 Y 变化，因为 Z>
- 修改：<文件:行号 / 参数，改前 → 改后；单变量>
- 判据：<成功 = 指标 A 达到…；失败 = 出现…>
- 动作：具体做了什么（含回退方式：<命令>）
- 证据：日志行 / 计数 / md5，贴原文不转述
- 结论：成功 → 保留并回写 TASKS；失败 → 已回退，切换假设 ExNN+1
- 现场变更：重启了哪些进程 / 改动了哪些文件（没有写「无」）
```

## 5. 代码修改要求

- 修改前检查 `git status`，确认改动范围已知。
- 保留可恢复的稳定版本。本项目惯例：远端原文件在 scp 覆盖前先
  `cp xxx.py xxx.py.bak_$(date +%m%d_%H%M)`；本地失败实验用 `git checkout -- <file>` 回退。
- 每次实验尽量独立，不同时修改多个无关模块。
- 失败实验及时回退；成功实验经必要回归测试后提交。
- **红线**：不得为快速验证而随意修改厂家 URDF、底层驱动和安全保护逻辑。
  本项目对应：`auto_enable:=false`（安全门禁）不得改；`move_speed` 等已定版参数不得顺手动；
  遥操控制模式以 canfd 定版基线为准，换模式必须作为独立实验声明。

## 6. 什么时候才需要深入根因分析？

出现下列**任一**情况才提高分析深度，否则一律按快速实验推进：

- 多次实验均无法解决问题。
- 问题可能涉及机械碰撞、设备损坏或人员安全。
- 不同实验出现相互矛盾的结果。
- 修改可能影响多个系统模块。
- 问题具有明显的随机性或间歇性。
- 临时方案可能掩盖底层结构性问题。

## 7. 最终目标

优先解决现场实际问题：先通过快速实验找到有效方案，再根据时间和项目要求补充根因分析、代码整理、回归测试和长期修复。

## 附录 A. 动真机前 30 秒安全红线速查

细节与踩坑原文见 AGENTS.md §4；这里是动手前快速过一遍的清单：

1. `auto_enable:=false` 不得改；使能必须操作员在示教器 / 5566 人工确认。
2. `move_speed`、控制模式等定版参数不得顺手改；要动必须先声明为实验变量并落账。
3. J7 停在 ±170° 限位附近——离核实机时手不要扶在关节上。
4. TCP 30485 单连接：跑直连探针（joint_probe 等）前先停 T3 bridge。
5. 杀进程用 `pgrep -f "拼接""关键字"` 或按 PID；禁止 `pkill -f` 自匹配、禁止 `pkill -9` 打 ros2 launch。
6. 重启链路一律用 `~/桌面/dm-exo/restart_teleop.sh`，重启后按 AGENTS.md §3.1 的四条证据判成功。
7. 真机突停 / 堵转先走 fault 流程（`probe_device_state` → 5566 人工清障 enable），
   不要反复杀起 bridge 当修复。

## 附录 B. 真机实验的最小安全条件（每次开始前逐项确认）

- [ ] 工作空间内无人、无障碍，急停路径畅通，操作员手按离合 / 急停随时可断。
- [ ] 先跑无离合基线：`sent=0`、`reject=0`、`max_err=0` 才算干净起点。
- [ ] 动作低速、小位移，先单关节 / 单方向，确认后再放大。
- [ ] 出现 `program_run_failed` 或 `max_err` 增大：立即停止实验，记录日志原文后回退。
- [ ] 实验结束恢复定版参数，重启对应进程并复验基线。

## 附录 C. URDF 真机验收检查清单（适配前 P0 门禁，逐项确认）

> **URDF 正确性是适配前优先检查对象**：不匹配的 URDF 禁止接入遥操链（IK/限位/碰撞/RViz）。
> T20 实锤代价：结构性残差 292~1895mm、姿态残差 100~167°、方向反、下游校准全部被卡。
> 五道门串行，任一门不过禁止进下一门。完整流程与判决处置见 [URDF真机验收方案.md](./URDF真机验收方案.md)。

- [ ] **G0 资料层**：URDF 来源/版本/修改记录可追溯，md5 落台账；限位三方一致
      （URDF = 档案 = 实机直读，不一致以实机直读为权威并逐轴列差）。
- [ ] **G1 静态结构层**：关节名/序/数量与协议一致；轴向齐性；左右臂镜像性 diff；
      零位定义（URDF 零位 vs 电机零位）；末端无漏掉的固定旋转/工具偏移。
- [ ] **G2 自洽层**：同一 URDF 下 TF vs pinocchio FK 恒等（0.0mm/0.0°）——
      只证实现自洽，**不证匹配真机**，不得拿本门当真机检查。
- [ ] **G3 真机对账层（核心）**：≥20 组独立构型 (q, get_tcp_pose)，只读优先；
      双维度残差 位置 ≤20mm 且 姿态 ≤2°；判决三分支——PASS / 符号可救（翻转表修正后重验）/
      结构性不可救（禁止接链，走厂商索取或 URDF 自重建，重建产物回本门重验）。
- [ ] **G4 冻结与回归**：通过版 md5 + 验收报告入台账；此后每次标定/重部署/换件后
      跑 5 组简版回归（防标定复活旧病）；链上所有 URDF 副本与通过版 md5 一致。

**数据需求与采样分档**：G0/G1/G2 纯桌面零真机成本，先做完再约窗口；仅 G3 需真机——
且**采样 ≠ 驱臂**（首选操作员摆位 + 脚本只读采集，零运动指令）。采样分档：粗判决 6 组 /
标准验收 20 组（双维度门限）/ 重建 60 组（仅判「不可救」走 T39 时）；一批数据多处复用
（G3 判决 → 重建种子 → 回归基线），不是每次适配从零采。
