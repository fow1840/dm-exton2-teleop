# 日志观测性评估：关键节点加日志能否更快定位模块问题

- 日期：2026-11-06（评估 + 部分实现，见 §四）
- 结论先行：**能，且是当前性价比最高的改造**。本周每个跨模块难题都靠「录包+离线分析」
  才能归因，而其中一半问题若当时有日志本可当场定位。核心缺口不在"日志多少"，
  而在三个结构性缺陷：① T5 ik_node 运行期日志为零（仅 3 条启动日志，250Hz 主循环
  完全黑盒）；② 各节点计数器是**自启动累计值**，看不到窗口速率；③ 跨节点事件
  （离合沿/冻结沿/拒绝）没有可对齐的时间线。

## 一、本周真实案例复盘：日志本可省下的时间

| 案例 | 当时怎么定位的 | 若有日志 |
|---|---|---|
| T12「IK 冻结了 bridge 还在发吗」 | 拒绝计数 19→59 + 录包离线分析 ik_rng/rob_rng 对齐（数小时） | ik_node 状态行打印 `still=1 frozen=1`，bridge 状态行打印 `sent+2s 增量`——两条日志一对照即知 |
| T11「目标自己滑移还是 IK 追残差」 | clutch_probe 录包 + 离线重放 | 链路监视器在线打印「手静窗目标速度 20mm/s」直接实锤 |
| R2「ack 是受理还是完成」 | 无日志可查，只能靠 timeout 计数推断（25/2092） | bridge 记录每条 movej 发出→ack 延迟分布，配合反馈静止时刻可在线推断 |
| 幽灵 TF（更早） | FK 输出整体错位，排查半天 | 若 fk_adapter/监视器有「TF 帧来源/时间戳跳变」检测，当场报警 |

## 二、逐节点现状与缺口

| 节点 | 现状 | 缺口 | 可补性 |
|---|---|---|---|
| S4 ik_node | **仅 3 条启动日志**；运行期无任何输出 | 离合沿、锚定完成、冻结进出、solve 率、目标新鲜度全不可见 | ✅ 代码在手，P0 |
| S6 bridge | 较好：2s 状态行+拒绝计数+lock-step 统计 | ①计数器为累计值无窗口增量；②skip 只反映最后一拍；③无 fb 年龄；④无窗口内 hold/jump 占比 | ✅ 代码在手，P0 |
| S3 Puppetry / S2 MessageBridge | vendor 黑盒，仅启动日志 | 无法内部加日志 | ⚠️ 外挂只读监视器（UBT 同款 `pink_signal_chain_monitor` 思路），P1 |
| S5 fk_adapter | 仅 1 条启动日志 | yield 切换、TF 异常不可见 | 价值低（S4/S1' 监视器可覆盖），暂不动 |
| S7 控制器 | 无日志（协议查询） | 固件内不可加 | 用 probe/采集脚本替代 |

## 三、方案：A/B/C/D 四项（P0 两项已实现，P1 一项立项）

### A（P0，已实现）ik_node 运行期状态行 + 事件日志
- **2s 状态行**（与 T3 状态行同节拍，天然可对齐）：
  `IK_STAT clutch=L:1,R:0 still=L:1,R:1 anchor_wait=L:0 frozen=L:1 solve=0/500 cmd=500 win=2.0s`
  （solve 率直接暴露「双臂掉频」→ T18 的在线判据；frozen 与 T3 sent 增量对照 → T12 在线判据）
- **事件日志**（只在边沿打，不刷屏）：
  `clutch left ON（按臂重置 7 轴）` / `anchor left settled after 0.72s` /
  `freeze left ENGAGE (target_v=3.1mm/s)` / `freeze left RELEASE (target_v=8.2mm/s)`
- 回答：T11（目标滑移→freeze 反复进出的边沿频率就是滑移证据）、T12（frozen=1 而
  T3 sent 在涨 → hunt 实锤）、T18（solve 率掉没掉）、按下瞬跳（锚定耗时异常）。
- 约束：250Hz 循环内**不做 IO**，只累计计数器；状态行 2s 一条；事件仅边沿。
  纯日志添加，不改任何控制语义。

### B（P0，已实现）bridge 状态行窗口化增强
- 原：`sent=3274 movej_tx=2092 ack=2092 timeout=25`（累计，要心算差值）
- 增：`+2s: sent=N cmd_rx=N movej_tx=N reject=N | fb_age=0.03s max_err=0.031rad
  held=7 jump=0`（fb_age=R3 在线观测；max_err/held=最后一拍计划上下文；
  reject 增量与 ik_node freeze 边沿对齐 = T12 判据）
- 兼容：保留原累计字段，证据链（历史日志比对）不断。

### C（P1，立项 T21）独立链路监视节点 `chain_monitor`
- 形态：**独立只读进程**（不碰任何控制路径，vendor 黑盒的外挂眼睛），
  UBT `pink_signal_chain_monitor.py` + `cmd_gap_monitor.py` 同款思路。
- 订阅：(C) target×2、(E) state×2、(F) commands、(D) client_joint_states、(B) clutch×2。
- 计算并 2s 打印：
  - **目标流速度**（手静窗滑移 mm/s——T11 的在线判据，替代离线重放）
  - (E) 发布者数量与帧源鉴别（双发布=机制②报警；指令FK vs 实测FK 残差）
  - (F)→(D) 指令-反馈滞后（关节级，跟随延迟在线可见 → T15 的连续版）
  - clutch 事件时间线（所有模块日志对齐的基准线）
- 风险：零（只读）；代价：一个新节点 + 启动脚本挂载。

### D（规范）时间戳与格式纪律
- 所有新增状态行统一 2s 节拍 + `[组件] 前缀`；事件日志带 `time.monotonic()` 秒值——
  跨日志对齐只看秒差，不做时区换算（T3/T5 同机时钟，天然一致）。

## 五、日志解决不了的事（诚实边界）

- **ack 语义的最终确认**：日志能给出延迟分布的强倾向，但受理 vs 完成仍需 T12 单步
  台架一锤定音；
- **控制器内部行为**（拒绝原因细分、队列、会话状态）：固件黑盒，只能靠协议查询命令；
- **外骨骼硬件层**：S1 不可观测，jump/漂移只能从 (A) 话题侧反推；
- 任何日志都替代不了录包：日志回答"有没有/多频繁"，包回答"逐帧因果"。
  两者是分层关系，不是替代。
